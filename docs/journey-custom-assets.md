# Journey custom asset contract

Custom Journey assets must remain portable between the web renderer and a
future Expo/Skia adapter. They are presentation data and must never contain or
replace Goal, milestone, route, progress, or character-position state.

## Accepted assets

- Environment: PNG or WebP, approximately 5:3, 600×360 through 2400×1440,
  maximum 5 MB.
- Character sprite: PNG or WebP with transparency, one horizontal row of
  32×32 frames, 2–12 frames, maximum 2 MB.
- SVG is intentionally rejected because user-provided active markup is not a
  safe image-upload format for this feature.

## Built-in character art standard

- The protected original Bat remains the visual-weight reference and is never
  regenerated by the sprite build pipeline.
- Production v3 characters fill most of a 32×32 frame, use a stable body or
  ground anchor, hard nearest-neighbour pixels, binary alpha, a 1–2 pixel dark
  outline, and no more than seven flat colours.
- Source generations stay outside runtime assets. Run
  `node scripts/build-journey-sprites.mjs` to normalize approved chroma-key
  sources into reusable 256×32 RGBA sheets under `public/animals/v3`.

The shared metadata validator is `src/lib/journeyCustomAssets.ts`. Backend
validation must repeat these checks from decoded file bytes; frontend checks
are only early feedback and are never a security boundary.

## Storage boundary

Do not write uploads into the deployed Next.js `public/` directory and do not
store device-local paths on Goal. Production implementation needs private
object storage with immutable generated keys, content sniffing, size limits,
owner metadata, and a delete lifecycle. Goal should store only an asset ID.

Recommended future API:

- `POST /user/journey-assets` validates and stores an asset.
- `GET /user/journey-assets` lists assets owned by the current user.
- `DELETE /user/journey-assets/{id}` soft-deletes an unreferenced asset.
- Goal presentation fields reference `environment_asset_id` or
  `character_asset_id`; built-in theme/character IDs remain the fallback.

Custom uploads remain disabled until an object-storage provider and retention
policy are selected. This avoids a local-only implementation that would break
mobile clients and multi-instance deployments.
